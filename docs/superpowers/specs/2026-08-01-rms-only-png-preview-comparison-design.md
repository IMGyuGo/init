# RMS 전용 PNG 립싱크 비교 미리보기 설계

## 배경

현재 운영 면접관은 PNG 기반 렌더러를 유지하면서 RMS를 발화·무음 판정에 사용하고, 발화 중에는 한국어 텍스트 Viseme 타임라인의 `rest`, `closed`, `open`, `wide`, `round`, `teeth` 입 모양을 우선한다. 이후 추가된 입 벌림 단계와 스프라이트 정렬 보정 때문에 현재 화면만으로는 초기 립싱크 동작과 결과를 직접 비교하기 어렵다.

비교 대상인 수정 전 버전은 `a7d4abe8` 적용 직전 동작이다. 이 버전은 오디오 분석기를 사용할 수 있을 때 RMS만으로 다음 세 상태를 선택했다.

- RMS가 무음 임계값 이하이면 `rest`
- RMS가 무음 임계값보다 크고 열린 입 임계값 이하이면 `closed`
- RMS가 열린 입 임계값보다 크면 `open`

이 설계는 해당 동작을 운영 면접에 되돌리지 않고 `/interviewer-preview`의 QA 전용 비교 대상으로 복원한다.

## 목표

- 동일한 로컬 QA 음원을 현재 방식과 수정 전 RMS 전용 방식에 동시에 전달한다.
- `/interviewer-preview`에서 두 PNG 렌더링 결과를 나란히 비교한다.
- 수정 전 방식은 실제 과거 임계값과 `rest → closed → open` 전환 규칙을 재사용한다.
- 현재 운영 면접 화면과 기본 PNG 렌더링 동작은 변경하지 않는다.

## 비목표

- 실제 모의 면접 또는 채용 면접에 렌더러 선택 기능을 추가하지 않는다.
- `open-small`, `wide-small`, `round-small` 스프라이트를 수정 전 방식에 사용하지 않는다.
- Cubism 렌더러 또는 신규 이미지 에셋을 추가하지 않는다.
- RMS 임계값, Viseme 타임라인, 저장된 립싱크 튜닝값을 재설계하지 않는다.
- API, 데이터베이스, 환경변수 또는 배포 계약을 변경하지 않는다.

## 검토한 접근

### 1. 하나의 분석 결과를 두 렌더러가 공유하는 나란히 비교 — 선택

`useLipSyncDriverState`가 이미 계산하는 RMS를 출력 상태에 포함한다. 현재 렌더러는 기존 `mouthShape`을 사용하고, 수정 전 렌더러는 같은 프레임의 RMS를 기존 `getMouthShapeForRms`에 전달한다. 하나의 Web Audio 분석기만 사용하므로 두 결과가 같은 음원 시점에 동기화되고, 동일한 `HTMLAudioElement`에 분석기를 중복 연결하는 브라우저 오류를 피한다.

### 2. 현재 방식과 수정 전 방식을 토글

한 화면만 렌더링해 구조는 단순하지만, 두 방식의 지연과 모양 차이를 같은 음원 시점에 직접 비교할 수 없다. QA 목적에 비해 관찰성이 떨어져 선택하지 않는다.

### 3. 수정 전 전용 립싱크 훅과 오디오 분석기 복제

과거 구현을 독립적으로 보존할 수 있지만, 하나의 미디어 요소에 `createMediaElementSource`를 중복 적용할 위험이 있고 분석 시점도 달라질 수 있다. 기존 설계에서 이미 피하고 있는 실패 경로이므로 선택하지 않는다.

## 설계

### 립싱크 상태 경계

`LipSyncDriverState`에 정규화하지 않은 현재 RMS 값을 읽기 전용 숫자로 노출한다. 값은 기존 분석 루프에서 계산한 상태를 그대로 반환하며, 새 분석기나 별도 타이머를 만들지 않는다. 오디오 분석을 사용할 수 없거나 말하지 않는 상태에서는 기존 상태 초기화에 따라 0을 반환한다.

현재 운영 소비자는 새 필드를 사용하지 않으므로 `InterviewAvatar`와 실제 면접 동작은 그대로 유지된다.

### 수정 전 렌더링 경계

별도의 과거 컴포넌트를 복제하지 않는다. `/interviewer-preview`에서 기존 `LocalInterviewerAvatar`에 `getMouthShapeForRms(rms)` 결과를 전달한다. 이 방법은 당시 RMS 선택 규칙은 정확히 재현하면서 자세, PNG 에셋 위치, 접근성, 모션 감소 처리는 현재 공용 렌더러와 공유한다.

수정 전 결과는 `rest`, `closed`, `open`만 활성화한다. `wide`, `round`, `teeth` 또는 작은 입 스프라이트로 전환하지 않는다.

### 미리보기 화면

기존 `RMS 오디오 입력` QA 영역의 결과 열을 두 칸으로 구성한다.

- `현재 · Viseme + RMS`: 현재 `lipSyncState.mouthShape`을 렌더링한다.
- `수정 전 · RMS 전용`: 같은 `lipSyncState.rms`에서 계산한 과거 입 모양을 렌더링한다.

각 카드에 방식 이름과 현재 입 모양을 텍스트로 표시한다. 좁은 화면에서는 두 카드를 한 열로 쌓는다. 기존 재생 버튼, 오디오 컨트롤, 관찰된 현재 입 모양 기록은 유지한다.

### 데이터 흐름

1. 사용자가 로컬 QA 음원을 재생한다.
2. `useLipSyncDriverState`의 단일 Web Audio 분석기가 최대 30 FPS로 RMS를 계산한다.
3. 현재 카드에는 기존 Viseme 우선 결과인 `mouthShape`을 전달한다.
4. 수정 전 카드에는 같은 RMS를 `getMouthShapeForRms`로 변환한 결과를 전달한다.
5. 재생 정지, 종료 또는 모션 감소 시 두 카드 모두 `rest`로 돌아간다.

## 오류와 접근성

- 오디오 재생 실패 상태와 오류 문자열은 기존 QA 루트에 유지한다.
- 분석기를 사용할 수 없으면 현재 방식은 기존 텍스트 타임라인 대체 동작을 유지하고, 수정 전 방식은 RMS 0에 따라 `rest`를 표시한다.
- 두 비교 카드의 제목과 현재 입 모양은 화면에서 읽을 수 있는 텍스트로 제공한다.
- 모션 감소가 켜지면 두 렌더러 모두 입 움직임을 비활성화한다.
- 비교용 데이터 속성은 현재 방식과 수정 전 방식을 명확히 구분해 자동 검증에서 잘못된 렌더러를 선택하지 않게 한다.

## 테스트

테스트를 먼저 추가하고 다음 RED를 확인한다.

- `useLipSyncDriverState` 출력 계약에 RMS가 포함되지 않아 실패한다.
- RMS QA 마크업에 현재 방식과 수정 전 방식의 구분된 비교 카드가 없어 실패한다.
- 수정 전 카드가 RMS 전용 `rest`, `closed`, `open` 규칙을 사용하지 않아 실패한다.
- 수정 전 카드가 작은 입 스프라이트 또는 텍스트 Viseme 결과를 선택하면 실패한다.

구현 후 다음을 확인한다.

- 후보자 아바타 대상 테스트
- TypeScript 타입 검사
- 프로덕션 빌드
- `git diff --check`
- Windows Role D 로컬 하네스
- `/interviewer-preview`에서 로컬 음원 재생 시 두 카드가 동시에 움직이고, 수정 전 카드는 `rest`, `closed`, `open`만 표시하는 브라우저 QA

## 완료 기준

- `/interviewer-preview`에서 현재 PNG 립싱크와 `a7d4abe8` 직전 RMS 전용 동작을 동일 음원으로 나란히 볼 수 있다.
- 두 결과는 하나의 오디오 분석기와 동일 RMS 샘플을 공유한다.
- 수정 전 카드에는 `open-small`, `wide-small`, `round-small`, `wide`, `round`, `teeth`가 활성화되지 않는다.
- 실제 면접의 `InterviewAvatar` 호출 경로와 기본 렌더링 결과에는 변경이 없다.
- 자동 테스트, 빌드, Role D 로컬 하네스가 통과한다.
